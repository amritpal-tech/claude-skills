## Pankaj Kumar · GTM engineer

**Slot:** off today · banked for **Tue 17 Nov · 22:30 IST** (09:00 PT) · **Pillar:** Changelog reads · **Archetype:** technical truth-teller · **Rung:** 3 (advisory Oct 28, labelled "late October"; current stable Nov 13)

### Research brief
- **What happened:** n8n advisory GHSA-9p7v-45m2-wxgj, "Deprecated Code Nodes Allow Code Execution in the n8n Main Process", published Oct 28, 2026. Severity High, CVSS 8.7. The Function and Function Item nodes run user code in the vm2 sandbox; the LangChain Code node runs user code directly in the main process. An authenticated user who can create or modify workflows could run arbitrary code in the main process, outside the task runner isolation that applies to the Code node.
- **The fix:** patched in 2.42.6, 2.43.3, 2.44.0, 3.0.1 and later. A block, on by default: saving a workflow that adds or modifies one of these nodes is rejected; workflows already saved with them continue to run. `N8N_DEPRECATED_NODES_BLOCK=false` disables the block and restores the vulnerable behaviour. Workarounds: add `n8n-nodes-base.function`, `n8n-nodes-base.functionItem` and `@n8n/n8n-nodes-langchain.code` to `NODES_EXCLUDE`; limit workflow edit rights to fully trusted users. Recommended: upgrade, review workflows, replace with the Code node, keep the block on.
- **Current release:** n8n@2.47.7, marked Latest on GitHub, Nov 13.
- **Source:** [GitHub security advisory](https://github.com/n8n-io/n8n/security/advisories/GHSA-9p7v-45m2-wxgj) (primary, opened) · [n8n releases](https://github.com/n8n-io/n8n/releases) (opened)
- **Why it matters to the reader:** GTM engineers run Clay → n8n → HubSpot flows on self-hosted n8n, and older flows often still use Function nodes. They keep running, but nobody can edit them after the upgrade.
- **What the source does not say:** whether n8n Cloud instances needed action (the advisory is for the npm package); how many workflows use these nodes.
- **Angle:** the trap is the second line: it runs until the day you need to fix it. Find them, rebuild them, upgrade, keep the block on, cut edit rights.

### Post
<!-- post:pankaj format:single-image ask:sharp-question type:news -->
Your old n8n Function nodes still run. You can't edit them.

In late October, n8n published a high-severity advisory, CVSS 8.7.

The Function and Function Item nodes run user code in the vm2 sandbox. The LangChain Code node runs it directly in the main process.

So anyone who could create or edit workflows could run code in the main process, outside the isolation the Code node gets.

The fix is a block, on by default from 2.42.6, 2.43.3, 2.44.0 and 3.0.1:

↳ Saving a workflow that adds or changes one of those nodes is rejected.

↳ Workflows already saved with them keep running.

That second line is the trap. The workflow runs until the day it breaks and you need to change it.

What I'd do this week, in this order:

1. Export your workflows. Search the JSON for n8n-nodes-base.function, n8n-nodes-base.functionItem and @n8n/n8n-nodes-langchain.code.
2. Rebuild each one in the Code node. Pin the same test data and compare outputs before you switch.
3. Upgrade to a patched version. The latest stable is 2.47.7, from November 13.
4. Leave N8N_DEPRECATED_NODES_BLOCK on. Setting it to false brings the vulnerable behaviour back.
5. Give workflow edit rights only to people you'd trust with the server.

The part most RevOps teams will hate: on those versions, workflow edit rights were server rights.

One tool, one job. The Code node runs code. Retire the rest.

Which old node is still holding up a workflow in your stack?
