Your WordPress blog could be ranking for someone else's malware.

On November 16, the FBI published a FLASH alert on Gootloader, malware spread through SEO poisoning and hacked websites.

Per coverage of the alert: as of October, the FBI had found more than 1,000 infected WordPress sites and 216 domains run by the operator, tied to more than $28 million in ransomware payments.

Here's the mechanism SEO teams should care about.

The attacker doesn't need your rankings. It borrows your domain's trust with pages you never published.

Where I'd start this week:

1. Run a site: search on Google for your domain with words like "agreement", "template" or "download". Look for pages nobody on your team wrote.
2. Open Search Console's Security issues report.
3. Turn off xmlrpc.php if nothing uses it. Coverage of the alert says the FBI recommends it.
4. Patch WordPress core, plugins and themes, and put MFA on admin and hosting logins.
5. Ask whoever runs the site to alert on unexpected changes to theme, plugin and JavaScript files.

The honest limit: updating WordPress doesn't remove a lure that's already there. Finding it does.

Your domain's trust took years to build. Guard it like a ranking.

When did someone last check which pages Google has indexed on your domain?

<!-- post:pankaj format:text ask:sharp-question type:news -->
The next n8n release puts guardrails on agent tool calls.

Version 2.49.0 went out on November 17 as a pre-release. The latest stable build is still on 2.48.

Two lines in the changelog matter most:

"Agent config schema now can include tool guardrails."

"Run pattern-based tool guardrails on agent tool calls."

In plain terms: you write rules into an agent's config, and n8n checks its tool calls against them.

For a GTM agent with CRM and email access, that's where I'd block the calls you never want: deletes, bulk updates, sends to anyone outside the sequence.

Then read the rest before you upgrade:

1. Approval requests now work in the agent's webhook channel, and that channel is renamed "API". Update your runbooks.
2. Unattended task approvals now sit in a new "waiting" status. Add it to whatever alerts you on stuck runs.
3. The MCP tool that deleted agents is replaced by one that archives them.
4. AI nodes that use API key credentials now require an API key. Check the workflows that rely on them.
5. Outbound MCP OAuth now follows the 2026-07-28 authorization spec. Retest every MCP connection after the upgrade.

The catch for RevOps: guardrails are config. Someone has to write them, review them and own them like a permission set.

No agent touches the CRM without a written list of the calls it may never make.

Which tool call would you block first?
